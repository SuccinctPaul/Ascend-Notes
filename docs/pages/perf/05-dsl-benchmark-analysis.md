# 05 · 仓库实测：4 种 DSL 的性能 / 精度对比解读

`>` 面向 0→1 新手：把这仓库 README 那几张表格，翻译成"为什么另一个 DSL 更快 / 为什么这个精度差一点 / 每种写法到底代表哪种抽象层级"。
`>` ⚠️ 本文所引数字**全部来自本仓库 README 实测**，不是凭空编的；但"为什么"的解释属推理，凡属推测处我都明确标注"（推测/可能原因）"。

---

## 概述

同一个 `C = A @ B`，用 4 种写法实现，测出来的数字长得不一样。数字背后透露出的是：**每种 DSL 把"控制硬件"这件事交到了谁手里**。

一句话先给结论：

- **python 慢**，是因为它在 CPU 上用解释器一阶一阶跑，根本不是 NPU 的东西，只当"正确答案参考"。
- **triton 比 tilelang 慢**，因为它把大多数优化（分块/流水/调度）交给编译器，而它在昇腾后端还不能像 tilelang 那样贴着 Cube 走。
- **tilelang 快且精度略差**，因为它显式地占了 L1/L0C、明显更贴近 Cube/引擎，而精度上的那点差异大概率出在**累加顺序或累加精度**上。
- **ascend_c 实际耗时未测出（表里是 "—"）**，它是控制粒度最细、也是工作量最大的那一个。

**人话**：抽象越高的写法越省事但越"隔着一层"，抽象越低的写法离硬件越近、上限越高但要你亲手管。

---

## 为什么需要

- 你要选 DSL：先要知道"慢"是用错了地方，还是"这个抽象层次本来就离硬件远"。
- 你要判断要不要为性能下沉：看 `05` 的数据，就知道"多给你多少性能、代价是什么（代码量/精度）"。
- 你要看懂精度差异：避免想当然以为"越快的越不准"，或反过来。

**人话**：今天这份数据就是"卖多少力气换多少性能"的价签。

---

## 定义（抽象梯子，沿用 CONTEXT.md 的"抽象梯子"术语）

| 术语 | 含义 |
|---|---|
| **抽象梯子** | 四种 DSL 对"内存层级 / 搬运 / 调度"的控制颗粒度不同：字节级 → 块级 → 调度级 |
| **字节级（最低）** | 你能直接指到每个元素、每次搬运、每块缓冲（ascend_c） |
| **块级（中）** | 你描述"块"，缓冲/分块/调度由编译器决定（triton） |
| **调度级（中偏调度）** | 你显式指定缓冲与流水，但有高层原语（tilelang） |
| **正确性基准** | examples/python/np.matmul 用于对拍，不参与性能比较 |

## 主体

### 1）先把 README 的实测数字摆出来

四列对应关系（128³，fp16 输入，fp32 累加器）：

| DSL | NPU 上是否跑通 | `max_abs_error`（对齐参考基准） | 耗时（128³ fp16） |
|---|---|---|---|
| `examples/python/`（CPU 基准） | —（不跑 NPU） | 0.0（vs np.matmul） | **4.27 s**（朴素三重循环） |
| `examples/triton_ascend/` | ✅ | **0.0** | **0.79 ms** |
| `examples/tilelang_ascend/` | ✅ | **9.77e-04** | **0.38 ms** |
| `examples/ascend_c/` | ✅ | **0.0** | —（README 未给耗时） |

三个直接对比维度：
- **CPU vs NPU 量级差距**：`4.27 s` 对比 `0.79 / 0.38 ms`——差了约 **5000~11000 倍**。
- **NPU 内部，tilelang 比 triton 快 ~2.1 倍**（0.79 → 0.38 ms）。
- **精度：triton 与 ascend_c 是 0.0（完全对齐），tilelang 是 ~9.8e-4（非零但很小）**。

### 2）为什么 python 4.27s 那么慢（这是"参考"不是"对手"）

- 128³ 的 GEMM 只有约 4.2 MFLOP（见 `01`），理论上一眨眼就算完。
- 但**朴素三重循环 + 解释器**：每个元素的操作都被解释器一层层翻译，加上 Python 层面的循环/索引开销，开销远大于那点浮点运算本身。
- 它也不在 NPU 上跑，纯 CPU 单线程、无向量化加速（在 `01` 的 Roofline 里根本不在 NPU 屋顶体系内）。
- 所以它的角色**只是"正确性基准（ground truth）"，不是性能对手**。拿它与 NPU 比速度没有意义。

**人话**：python 是"对答案用的草稿"，比速度请直接看三个 NPU 的实现。

### 3）为什么 tilelang（0.38 ms）比 triton（0.79 ms）快

这是本仓库最有信息量的一问。关键在"**谁在控制硬件**"（抽象梯子）：

- **triton（块级）**：你写 `make_block_ptr + tl.dot`，里面具体怎么 tiling、开几级流水、怎么切核，**大部分交给 triton-ascend 后端编译器**去猜。编译器在昇腾后端往往给不出最贴硬件的方案（tile 偏大/流水级数不够/调度不够细），于是 Cube 利用率和对搬运的隐藏都打折扣（对应 `04` 症状二 / 症状四）。
- **tilelang（调度级）**：你**显式的 `alloc_L1/L0C`、`T.copy`、`T.gemm_v0`、`T.Scope("C")`**，把 Ascend 的内存层次（L1 / L0C）和 Cube 调度直接说给编译器，还常自动做 layout inference + 多级流水。贴 Cube 越近，利用率越高 → 更快。

`>` 这段是"为什么更快"的主流解释，但**0.79 与 0.38 的差距里有多少来自实现细节、多少来自后端成熟度，需要你结合各目录源码与 profiling（`03` 的 msprof op）实测确认**（推测成分标注）。

**人话**：triton 让编译器代劳但编译器在这块板上还不太会干活；tilelang 把调度拿到明面上，所以赢在这。

### 4）为什么 tilelang 精度是 ~9.8e-4 而 triton/ascend_c 是 0.0

这是最容易想当然的一项——先纠正：**"快≠一定不准，准=一定不快"是错的**。这里是**累加细节**的差异：

- README 约定输入输出 fp16、累加器 fp32（CONTEXT.md：混合精度）。fp16 尾数才 ~11 位、约 3 位十进制有效数字，**累加 K 维时先后顺序会影响舍入**（CONTEXT.md 的"精度损失"）。
- **`triton` / `ascend_c` 报 0.0**：意味着它们的最终结果和参考基准（np.matmul）**逐位一致**。这通常发生在这几种情况之一（可能是）：
  - 累加顺序恰好和参考一致；
  - 数据取值偏"整"或偏小，fp16 表示下舍入恰好没造成可观测差异；
  - 三者都做 fp32 累加，而数值凑巧被完全保留。
- **`tilelang` 报 ~9.8e-4**：非零但很小。常见解释（**推测，需用各目录生成的数据与 log 确认**）：
  - 它的 `T.gemm_v0` 在默认配置下累加顺序或累加精度（比如某段在 fp16 桶里累加）与参考不同；
  - tile 切分后沿 K 的求和顺序和 np.matmul 不一样，极小项被（或不）舍掉；
  - 输入数据本身带浮点味道，fp16 表示下乘积的小数进位在 fp32 累加器里没被完全保留。

`>` ⚠️ 判断"哪种更准"不能只看 0.0 vs 9.8e-4：**能拿到 0.0 很可能是"碰巧一致"，不等于一定比 tilelang 数学上更稳**。要用更大的 K、更大范数、不同数据分布去压测，才能比出真正的精度鲁棒性（`03` 里也提醒过 msprobe 才是做精度比对的工具）。具体数据分布和断言，**请以该 DSL 目录的测试脚本与日志为准**。

**人话**：那 9.8e-4 大概率是"累加顺序/累加桶"不同造成的极小差别，不是 tilelang 坏了；0.0 未必就代表"更准"，只是"和 np.matmul 一字不差"。

### 5）ascend_c：控制最多、但耗时为何是 "—"

- ascend_c 是**抽象梯子最底层**：GlobalTensor 逐元素、显式 DMA、你手工决定 tiling/flow（`02` 就是它的主战场）。
- README 里它"跑通、max_abs_error=0.0、耗时 = **—**"。这个 "—" 表示**当前实测表没有填它的数值**，不代表"最快"或"最慢"。
- 正确看待：ascend_c 本可以逼近甚至超过 tilelang（只要你把 `02` 的 tiling/流水卷到极致），但**代价是代码量和工作量最大**。它适合"我对性能有极致的控制欲/必须逐字节优化"的场景。

**人话**：ascend_c 是"最原生态、最费手"的一条路，别因为它表格空着一格就误以为它没进度。

### 6）串起来：这张表告诉你该怎么选

| 你要什么 | 选 |
|---|---|
| 验证正确性 / 写参考解 | `examples/python/` |
| 上手快、代码少、性能尚可 | `examples/triton_ascend/` |
| 性能优先、又能接受不少顺手的显式调度 | `examples/tilelang_ascend/` |
| 极致的硬件控制 / 学习昇腾底层 / 前两者不够时 | `examples/ascend_c/` |

`>` 也得出结论：**从 triton 换到 tilelang，性能上一档、代码仍然很 Python；从任何 DSL 下沉到 ascend_c，是把控制力换到手、把开发成本背到身上。** 抽象层级（CONTEXT.md 的"抽象梯子"）刻画的就是这条"控制力 vs 成本"的取舍线。

### 8）新手 FAQ

- **Q：是不是一定要选"最快"的 tilelang？** 看场景。你先要**正确**（用 python 对拍），再要**够用**（triton 往往够），最后才谈**压满**（tilelang / ascend_c）。追求极致前先问"快 2 倍对我的部署值不值得多花钱/多花代码"。
- **Q：max_abs_error 用什么阈值判通过？** 本仓库用 `allclose(atol=1e-2, rtol=1e-2)`。`9.8e-4` 在这个阈值下是 PASS 的；要是你的场景对精度更敏感（比如 FP16 大 K 累加），可以降到更苛刻的阈值再看。**阈值由需求定，不是越接近 0 越好**。
- **Q：同一个 kernel 在不同的机子上会复现这组数字吗？** 不会完全一样。耗时随芯片频率/核数/温度浮动，**数字是趋势不是常量**；要复现结论，重跑 + 取多次平均 + 对拍（`03` 的步骤）。
- **Q：我想让 triton 逼近 tilelang 怎么办？** 把"编译器决定"改成"你告诉它"：显式 block 大小、开多级流水（如果后端支持）、必要时换到更显式的 DSL。这也是 `02` 教的事。

### 9）把数字放回 Roofline 上读（跨篇收口到 `01`）

`01` 教过：瓶颈只看"你离平顶近、还是贴斜边近"。把那几毫秒放回屋顶上，比"谁数字小谁赢"更有信息量：

- **这组 GEMM 的算术强度 I**：128³ 约 4.2 MFLOP；若按 A/B/C 各 128² 个 fp16 进出 HBM 一趟算，I ≈ 43 FLOP/B（`01` 里算过那个数）。对大多数昇腾，这大概率落在**带宽受限的一侧**。
- 因此 **MTE2/搬运占比** 往往是首个该盯的信号（`03` 教你测它多高，`04` 教你治它）。
- triton 0.79 与 tilelang 0.38 的差距，从 `01` 视角看，多半不是"谁碰到更高的算力峰值"，而是**谁把搬运藏得更满、谁更贴 Cube（利用率更高）**——这和 `04` 的症状二/症状四正好对上。

**人话**：这几毫秒不是"谁的 CPU 快"，而是"谁让 Cube 更饱、让搬运更少更藏"。快慢要放回"屋顶"上才读得懂。

### 10）你想自己把这组数字复现一遍，怎么做

别只信"别人报的数字"，最好动手复跑（README 里每一条命令都列了）：

```
① 每个 DSL 独立 venv：cd 目录 && uv sync
② python 基准本机就能跑；NPU 三目录要上昇腾服务器并 source 环境
③ ascend_c：cmake 构建 ./ascend_gemm 再运行（可顺手挂 msprof op 取 profile）
④ triton / tilelang：各自目录 uv run python src/test_gemm.py
⑤ 多跑几次取中位数，并看打印的 max_abs_error 与 PASS
```

- **看趋势，不看单次**：耗时随温频浮动，跑 3~5 次取中位数更稳（`03` 坑 D 也提过预热/取均值）。
- **复现不了一模一样很正常**——方法比常数重要：你要学的是"怎么对比、怎么读 profile"，不是背下 0.79 这个数。

**人话**：这组数会随机器浮动，但"tilelang 更贴硬件、triton 更省事、python 只对拍"这个**趋势**是稳定的，值得你在自己机器上验证一遍。

### 11）一句话定取舍（最终版）

| DSL | 用在哪 | 代价 | 当你想要… |
|---|---|---|---|
| `examples/python/` | 对答案 | 慢到没法比速 | 正确性基准 |
| `examples/triton_ascend/` | 快速上线 / 省事 | 性能一般 | 少写代码 |

## TL;DR

1. **python 慢** = 参考基准，不是速度对手。
2. **tilelang `>` triton** ≈ 谁更贴 Cube、谁更会把调度拿到明面上，谁就快（0.38 vs 0.79 ms）。
3. **tilelang 精度 ~9.8e-4** ≈ 累加顺序/累加精度的极小差别，不是"快就丢精度"；0.0 也只代表"和 np.matmul 一字不差"。
4. **ascend_c 是 "—"** = 没填耗时，不代表最快，它是最费手、上限最高的一条路。
5. 选型就一句话：**要正确→python；要省事→triton；要性能→tilelang；要极致控制/学底层→ascend_c。**

`>` 记住一句话：**这张表卖的其实是"你愿意亲手管多少硬件"——管得越多，性能可能越高，代码也可能越重。**
