# 04 · 常见瓶颈信号及对应优化手段

> 面向 0→1 新手：把 `03` 采到的信号，翻译成"改哪里"。这一篇是"症状 → 诊断 → 对症下药"的速查表。

**人话**：这就是一张"哪里疼按哪里"的优化菜单——先认症状，再下药，别乱补。

---

## 概述

Profiling 出来的数据，最终要落到一句判断：**这个算子卡在哪了？** 常见就几类：

1. **搬运算远了**（MTE/搬运占大头）→ 数据来回 GM 太多。
2. **计算没吃饱**（Cube/Vector 利用率低）→ 算力闲着，白花钱。
3. **带宽受限**（算术强度太低）→ 每次都搬一小点数据算一丁点，I 太小。
4. **多核没用匀 / 有空泡**（负载不均衡 / 流水没铺满）→ 部分核或某些时段在等。

**人话**：瓶颈逃不出"搬得辛苦、算得没吃饱、喂不饱、用不匀"这四种。

---

## 定义（几个"占用/利用率"信号先对齐）

| 信号（常来自 PipeUtilization / ArithmeticUtilization） | 含义（对应 CONTEXT.md 引擎） |
|---|---|
| **MTE2 / MTE3 占比** | DMA 从 **GM(HBM)** 搬进片上 / 从片上写回 GM 的时间占比 |
| **Cube 占比（aic_cube_ratio）** | **Cube 引擎**（矩阵乘）真正在算的比例 |
| **Vector 占比（aiv_vec_ratio）** | **Vector 引擎**（逐元素）在算的比例 |
| **Scalar 占比** | **Scalar 引擎**（控制/地址/循环）在跑的比例 |
| **核间不均衡** | 各核 `*_time` 差异大——有的核忙死，有的核闲死 |
| **空泡 / idle** | timeline 上某段谁都没干活的间隔（流水没填满） |

---

## 主体

### 1）症状一：搬运占大头（MTE2 / MTE3 高）

- **信号**：profiling 里 `*_mte2_*`（搬进来）或 `*_mte3_*`（写回）时间/占比很高，占到主要耗时。
- **根因**：数据一趟趟往 GM 里搬，搬的时间比算的时间还长（`01` 里那个 I 小、带宽受限）。
- **对症下药**：
  - **加 tiling / 放大分块**：让每次搬进来的数据在片上被复用更多次（`C[tm][tn]` 复用 A/B 的 tiles）。
  - **加深流水 / 加双缓冲**：让搬运和计算重叠（`02` 的多级流水），把搬运"藏"进计算。
  - **减少往返搬运**：能一次写完就别分多次写；能做融合（fuse）的算子合到一个 kernel 里，别中间结果反复进出 GM。
  - **提高数据复用**：B 的每一块尽量服务多个 C tile（比如把 K 维合进来一起算），别反复重读同一个数据。

> 一句话药方：**搬得太多 → 要么多复用，要么和算重叠，要么少搬。**

### 2）症状二：计算率低（Cube 利用率低 / 该用 Cube 没用到）

- **信号**：你的算子本质是矩阵乘，但 `aic_cube_ratio` 很低、大部分时间 Cube 在闲等（或根本没走 Cube，跑在 Vector/Scalar 上）。
- **根因**：
  - 没走 Cube：`trace`到了 Vector/标量逐个元素算，等于用脚杀牛。
  - 走 Cube 但空泡大：流水没铺、喂给 L0A/B 太慢、分块太小导致 Cube 起停开销大。
  - 控制流太重：Scalar 在算地址/判断，压住了 Cube。
- **对症下药**：
  - 确认算子真的用到了 **Cube**（`T.gemm_v0` / `tl.dot` / asc c 的 MMA 通路），而不是被降级成逐元素。
  - **把分块（tile）加大**到 Cube 舒服的粒度，减少 Cube 的启动/收尾开销。
  - **加深流水**，让 Cube 一直有活干（`02`）。
  - 把能向量化的控制流/地址计算从 Scalar 挪走，或减少循环层。

> 一句话药方：**Cube 闲了 → 确认在走 Cube、把块加够大、用流水把 Cube 喂满。**

### 3）症状三：带宽受限（算术强度 I 太低）

- **信号**：离"屋顶"的斜边（带宽墙）很近但够不着平顶（`01` 的 Roofline）；或吞吐被单核/单次搬运读出速率钉住。
- **根因**：每次搬的字节数相对于计算量太大，数据复用率低。
- **对症下药**：
  - **提高算术强度**：放大 tile、合并可复用的输入、尽量把 K 维的多步合到片上算。
  - **减少往返**：见症状一里的"减少往返搬运 / 复用"。
  - 必要时用 **L2Cache 切分**策略（数据放不下 L2 时，让它尽量命中 L2，避免都去 HBM 读写）。

> 一句话药方：**喂不饱 → 让每个字节多换几次计算（提高 I）。**

### 4）症状四：多核没用好 / 流水空泡

- **信号一·核少/不均衡**：`Block Dim` 远小于可用核数，或各核 `*_time` 差异大（一个累死，一群围观）。
  - 药方：`SetBlockDim` ≈ 可用核数（或 2 倍组合）；tile 切分要负载均衡（`02` 的多核并行）。
  - 尾块处理：整除不掉的余量统一分配，别让某个核多干一整块。
- **信号二·空泡**：timeline 上 Cube 和 DMA 不同时忙（一段算一段等）。
  - 药方：加深流水 / 双缓冲（`02` 的 overlap）。

> 一句话药方：**用不匀 → 核数开满、块切均衡；有发呆 → 铺流水。**

### 5）把四张症状串成排查套路

```
STEP 1  用 msprof op 采一发（03），看 PipeUtilization 谁占比最高
STEP 2  对照本表认症状：
          - MTE2/3 高        → 症状一 → 复用/流水/少搬
          - cube 低           → 症状二 → 走 Cube/加大块/铺流水
          - I 低 / 带宽受限    → 症状三 → 提算术强度
          - 核不均 / 空泡     → 症状四 → 开满核/均衡切分/铺流水
STEP 3  改完重采一发，对比两次占比，确认瓶颈比下降
STEP 4  有困难先回到 01 算算理论天花板，别在"够不到屋顶"的事上硬抠
```

> 同一份代码可能同时有几种症状——**先治占比最高的那个**，一次改一个变量，用数据验证，别一把梭。

### 6）怎样"量化"改完到底快了多少（判定法）

不要只靠 "看起来快了"。给一个新手可上手的三档判定：

```
① 算出"理论耗时"：搬运量 ÷ 带宽 或 计算量 ÷ 算力（取两者大者 ≈ 理论下限）
② 实测耗时 T_actual（用 03 的 profile / 多次运行取均值）
③ 判定：
   差距 < 20%      → 已经很贴理论，没必要死磕
   差距 20%~50%   → 有空间，回到本表认症状
   差距 > 50%     → 明显瓶颈，必须改
```

> ⚠️ 这个 20% / 50% 是社区常用来作为门槛的说法（我看到的是二手整理），**具体该用多少没有官方标准**，标"待核验"；
> 更重要的是——**反复对比优化前后的 profile**，只要某一条占比单调下降，方向就是对的。

### 7）把"症状 → 药方"做成一个表（速查）

| 你在 profile（03）里看到的信号 | 结论（症状） | 优先动作 | 对应章节 |
|---|---|---|---|
| MTE2/MTE3 占比最高 | 搬运是瓶颈 | 加 tiling、加深流水、提高复用、融合算子 | 02 |
| `aic_cube_ratio` 很低但算子本质是 MatMul | 没走好 Cube / Cube 空泡 | 确认走 Cube、加大块、铺流水 | 02/05 |
| 同规模读写每秒字节数提不上去 | 带宽受限（I 低） | 放大 tile、合并复用、提算术强度 | 01 |
| Block Dim 远小于核数 | 核没用满 | `SetBlockDim` 开满核 | 02 |
| 各核 `*_time` 差异大 | 核间不均衡 | 均衡切分、处理好尾块 | 02 |
| `*_scalar_*` 占比高 | 控制流太重 | 减少循环层 / 挪走地址计算 | 03 |
| timeline 有大段空泡 | 流水没铺满 | 加深流水 / 双缓冲 | 02 |
| `Current Freq < Rated Freq` | 被降频（DVFS） | 检查散热/电源配置 | 04-备注 |

**本仓库对号入座**：triton 与 tilelang 都写了 GEMM，若想压性能，首选从表中第一、二行下手（tiling/流水、Cube 利用率）；
ascend_c 则通常直接和 MTE2/流水/核均衡四行较劲。

### 8）新手 FAQ

- **Q：能不能一次把所有优化都加上？** 别。**一次只改一个变量，profile 对比后再改下一个**，否则分不清是谁的功劳。
- **Q：是不是所有算子都要做到"贴着头皮"才算好？** 不是。看需求：能跑、正确、（可选）够快即可；本仓库 128³ 这种小 GEMM，追求"贴 100%"意义有限，重点是**学会方法**。
- **Q：改完反而慢了？** 常见原因：tile 太大导致片上放不下/流水被迫降级、或同步点加多反而拖慢。回退一步、从结论反推是哪条改动引入的开销。

### 9）完整走查：从 profile 到改完（一组假想数字，只为演示流程）

> ⚠️ 下面是**演示用的假设数值，不是真实采集**，只为把"认症状 → 分先后 → 改 → 对比"的完整闭环走一遍。

假设你用 `msprof op` 采了一个 256×256 的 GEMM（读 `03`），得到：

```
op_summary：
    TaskDuration 最大的是 gemm_256
    Block Dim = 1                      ← 只开了一个核
PipeUtilization（单核）：
    ai*_mte2_ratio ≈ 0.60              ← 搬运占大头
    aic_cube_ratio ≈ 0.25              ← Cube 几乎在等
    ai*_scalar_ratio ≈ 0.03
```

**STEP A：认症状（对照第 7 节速查表）**

| 信号 | 症状 | 对应章节 |
|---|---|---|
| `Block Dim = 1` | 症状四：核没用满 | `02` 多核并行 |
| `mte2_ratio ≈ 0.60` | 症状一：搬运是瓶颈 | `02` tiling/流水 |
| `cube_ratio ≈ 0.25` 且本质是 MatMul | 症状二：Cube 没吃满 | `02` 铺流水 |

**STEP B：分先后——先治"最快见效"的**

- 三个里，`Block Dim=1` 属于"送分题"：明明有几十个核却只用 1 个。先把它开了。
- 改法：把 `SetBlockDim` 开到核数（或按 tile 切出足够多的独立块），让多核把负载摊开（`02`）。

**STEP C：改完第一轮，再重采**

- 核开满后各核 `mte2_ratio` 依然高 → 搬运仍是主矛盾，**一次只处理一个**（坑 C）。
- 接着做症状一：放大 tile 让 B 的每个块被多个 C tile 复用 + 加双缓冲把搬运藏进计算（`02`）。
- 预期 `cube_ratio` 上升、`mte2_ratio` 下降、`TaskDuration` 下降。

**STEP D：判定收敛（回到第 6 节）**

- 把"理论耗时"和"实测"比，差距 <20% 就收手，>50% 就继续。
- 关键不是一次到位，而是**每次只改一个变量、用两次采样的对比说话**（坑 E）。

**人话**：别一上来就想一次改完所有症状。**先开满核这种免费的，再啃搬运这种硬骨头，最后用对比数据确认收敛。**

### 10）更高一档：算子融合（fuse）——"少搬一次，就是赢一次"

当 GEMM 后面紧跟逐元素算子（如 ReLU、归一化）时，朴素做法是：

```
算子① GEMM  → 结果在 L0C( fp32)  →  DMA 跨域搬进 UB  →  Vector 算完 → 回写 GM
算子② ReLU  →                          再读回 GM → 在 UB 上算 → 再回写 GM
```

- **开销在哪**：中间结果 fp32 被写回 GM（HBM）又读回来一次。`01` 讲过的"带宽墙"就是这么被往返吃掉的。
- **融合做法**：把 ReLU 并进同一个 kernel——GEMM 的 L0C 结果（依然 fp32）**经 DMA 跨域搬进 UB 后立刻做 ReLU，只回写一次**。
- **本质**：减少"中间结果进出 GM"的次数 = 提高数据复用 = 让算术强度 I 变大 = 更远离带宽墙（`01`）。

> 融合不是"微优化"，而是**在搬运占大头（症状一）时最划算的一招**：把多个算子的多次往返并成一次往返。
> 融合能不能并、怎么并、在哪一层做，由产品/工具链支持；`04` 只教你判断"值不值得并"：
> **只要中间结果体积大、且被多次进出 GM，就值得尝试融合。**

**一个判断口诀**：看到两个算子首尾相接、前者的输出只喂给后者、中间结果还挺大 → 这俩就该考虑并进一个 kernel（对应仓库里三者的差异也见 `05`）。

---

## TL;DR

| 症状（信号） | 病根 | 下药 |
|---|---|---|
| MTE2/MTE3 高 | 搬得辛苦、往返太多 | 加 tiling、加深流水、提高复用、少往返 |
| Cube/Vector 利用率低 | 算力闲着 | 确认走对了引擎、把块加够大、铺流水 |
| 算术强度 I 低 | 每次搬的数据养不起够多的计算 | 放大 tile、合并复用、提 I |
| 核少/不均衡/空泡 | 用不匀、有发呆 | 开满核、均衡切分、铺流水 |

> 记住一句话：**先看谁占比最高，先治那个，改一个验一个，不要贪多。**
